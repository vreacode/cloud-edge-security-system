## 二、项目目标

本项目结合现有 Go2 四足机器人、外置深度相机和 PC 开发环境，构建一个用于校园走廊或实验室巡检的智能安防监控系统。

系统采用云边协同方式，将视频采集、初步处理、AI 识别、告警生成和人工处置分配给不同组件。

项目首先完成一条可演示的业务闭环：

采集画面 → 边缘初步处理 → PC 端 AI 识别 → 判断告警条件 → 记录告警 → Web 页面查看与处理。

软件工程实验的工作重点包括：

1. 需求分析与项目范围确定。
2. UML 分析模型和设计模型建立。
3. 云边职责划分与通信接口设计。
4. 数据库、后端和前端功能实现。
5. 功能测试、异常测试与部署说明。
6. Git 协作记录和实验报告编写。

机器人及相机作为系统的数据来源和应用载体。

## 三、产品愿景与应用场景

### 3.1 一句话价值主张

面向校园或实验室安防值守人员，利用机器人采集现场画面，通过云边协同识别指定区域内的人员事件，并提供可查询、可确认、可追溯的告警记录。

### 3.2 目标用户

- 安防值守人员：查看监控画面、接收告警并记录处理结果。
- 安防负责人：查看历史告警和处理情况。
- 系统管理员：维护设备、用户和检测规则。

### 3.3 核心演示场景

值守人员启用一台巡检设备，并设置一个监控区域。

设备采集画面后，边缘端进行抽帧、变化检测等初步处理，将候选画面发送到 PC 端。

PC 端调用 YOLO 或可替换的识别服务判断画面中是否存在人员，再结合监控区域和规则生成告警。

值守人员在 Web 页面查看告警时间、来源设备和截图，确认是否需要处理，最后填写处理结果。

上述流程属于拟实现方案，尚未代表已经完成实机验证。

## 四、初步系统方案

### 4.1 边缘侧

边缘侧负责：

1. 接入相机并采集画面。
2. 维护采集时间和设备标识。
3. 执行抽帧、变化检测等轻量处理。
4. 上传候选画面及事件元数据。
5. 上报设备在线状态。
6. 在通信失败时保留待重试数据。

具体边缘程序部署在 Go2 可用计算节点或配套计算设备上。

是否能够直接在机器人上运行所选程序，需要通过设备接入验证后确定。

### 4.2 PC 云端侧

使用 PC 模拟云端服务器，负责：

1. 接收设备状态和候选画面。
2. 调用 AI 服务完成人员识别。
3. 结合检测规则判断是否生成告警。
4. 保存设备、检测结果和告警记录。
5. 为 Web 页面提供查询和处理接口。
6. 记录关键操作和通信异常。

首版优先采用边缘轻量筛选、PC 端 AI 识别的分工。

如果后续验证边缘设备具备足够算力，可以评估将部分识别任务迁移到边缘端。

### 4.3 Web 应用侧

Web 页面负责：

1. 展示设备列表及在线状态。
2. 展示监控画面或最新截图。
3. 展示告警列表和告警详情。
4. 支持告警确认、处理和查询。
5. 支持必要的检测规则配置。
6. 展示基础告警统计。

### 4.4 云边通信内容

初步通信内容包括：

- 设备标识。
- 采集时间。
- 事件唯一标识。
- 候选截图或截图引用。
- 初步处理结果。
- 设备心跳与运行状态。
- 服务端接收确认。

具体通信协议在系统设计阶段确定。

设计时需要考虑请求超时、重复上传、网络中断和设备重连。

## 五、项目范围与需求优先级

采用 MoSCoW 方法划分需求优先级。

### 5.1 Must 必须完成

| 编号 | 需求 | 验收说明 |
| --- | --- | --- |
| M01 | 设备登记与状态查询 | 能识别设备来源并区分在线、离线状态 |
| M02 | 视频接入与画面展示 | 能展示接入画面或按约定频率更新的截图 |
| M03 | 边缘初步处理 | 能演示抽帧或变化检测等处理 |
| M04 | 人员识别 | 集成或模拟 AI 服务，返回识别类别、位置和置信度 |
| M05 | 检测规则 | 支持约定区域或条件下的人员事件判断 |
| M06 | 告警生成与保存 | 告警包含设备、时间、原因和截图 |
| M07 | 告警查询与人工处置 | 能查看、确认并记录处理结果 |
| M08 | 云边通信异常处理 | 对超时、重复上传和断线给出明确处理方式 |
| M09 | 关键流程测试 | 验证采集、上传、识别、告警和处置链路 |

### 5.2 Should 应当完成

| 编号 | 需求 |
| --- | --- |
| S01 | 用户登录与基本角色权限 |
| S02 | 检测阈值和告警规则配置 |
| S03 | 按设备、时间和状态筛选告警 |
| S04 | 同一事件的重复告警抑制 |
| S05 | 操作日志和基础告警统计 |

### 5.3 Could 可以扩展

| 编号 | 需求 |
| --- | --- |
| C01 | 告警记录导出 |
| C02 | 通过深度数据辅助估计距离 |
| C03 | 站内消息或其他通知方式 |
| C04 | 多设备接入展示 |

### 5.4 Won’t 首版不纳入

- 复杂自主导航与路径规划。
- 人脸身份识别。
- 跌倒、打架等复杂行为识别。
- 多机器人协同调度。
- 生产级云平台和大规模并发。
- 从零训练目标检测模型。
- 长时间完整高清视频存储。

## 六、五人分工

成员编号为临时占位，确定后替换为真实姓名。

每名成员负责自己的主要产出，同时参与需求讨论、交叉评审和最终汇报。

| 成员 | 主要职责 | 第一阶段主要产出 | 后续开发方向 |

| 成员 5 数据与测试负责人 | 领域分析、数据关系、验收规则 | 名词短语分析、CRC、领域模型、非功能需求 | 数据库、测试与验证 |

### 6.1 分工原则

1. 每项任务明确一个主要负责人。
2. 每项重要产出至少由另一名成员复核。
3. 组长负责整合，每名成员都要提交实质性成果。
4. 图、正文和术语由全组统一确认。
5. 每名成员能够解释自己负责部分及其相关接口。
6. 分工可根据实际能力调整，调整后更新本文件。

  - 角色列表包含名称、所属部门或类型、职责。

  - 设备与监控。

  - 图中有系统边界。

### T05 核心用例规约

- 负责人：成员 2
- 复核：成员 5
- 产出：至少 5 个完整核心用例规约
- 建议用例：
  1. 登记并接入设备。
  2. 查看监控画面。
  3. 配置检测规则。
  4. 识别事件并生成告警。
  5. 确认并处理告警。
  6. 查询历史告警。
- 每份规约至少包含：
  - 用例编号与名称。
  - 主要参与者。
  - 用例目标。
  - 前置条件。
  - 触发条件。
  - 基本事件流。
  - 备选与异常流。
  - 成功后置条件。
  - 失败后的保证。
  - 相关业务规则。

### T06 复杂用例活动图

- 负责人：成员 3
- 协作：成员 4
- 产出：至少 2 张 UML 活动图
- 建议流程：
  1. 画面采集、边缘处理、上传、AI 识别和告警生成。
  2. 告警查看、确认、处理、关闭及误报标记。
- 验收标准：
  - 清楚区分人员、边缘端、云端职责。
  - 决策分支具有条件。
  - 包含失败或异常路径。
  - 与用例规约的业务顺序一致。

### T07 名词短语法分析

- 负责人：成员 5
- 复核：成员 2
- 产出：候选类筛选表
- 验收标准：
  - 从场景和用例中提取名词短语。
  - 判断保留为类、作为属性或排除。
  - 解释判断理由。
  - 不将页面、按钮、数据库连接等实现概念直接作为领域类。

### T08 CRC 分析与领域模型

- 负责人：成员 5
- 复核：成员 4
- 产出：CRC 分析表、UML 领域模型
- 候选概念：
  - 用户。
  - 角色。
  - 设备。
  - 摄像头。
  - 视频源。
  - 检测任务。
  - 检测结果。
  - 检测规则。
  - 告警事件。
  - 告警处置记录。
- 验收标准：
  - CRC 表包含类、职责和协作者。
  - 领域模型显示关键属性、关联和多重性。
  - 告警来源和处理记录可以追溯。
  - 类之间的关系与实际业务一致。

### T09 非功能需求与验收条件

- 负责人：成员 5
- 协作：成员 4
- 产出：非功能需求清单
- 覆盖内容：
  - 告警及时性。
  - 通信可靠性。
  - 权限和数据访问。
  - 日志与可追溯性。
  - 维护和部署。
- 验收标准：
  - 需求有明确测量方法。
  - 性能数值标为目标，不能写成已经测得的结果。
  - 给出测试时的数据规模、网络和设备条件。

| R07 | 是否需要真实云服务器 | 向教师确认 PC 模拟云端的方案 |
| R08 | 模拟数据和实机数据如何区分 | 在演示和报告中明确标注数据来源 |

特别说明：

固定在画面上的区域，不会自动对应现实中的同一块地面。

如果机器人移动或相机转向，需要增加定位、姿态或场景映射能力，才能可靠判断现实禁区。

因此首版可以先让机器人移动到观察点，再在固定视角下完成检测与告警。是否扩展连续移动中的禁区检测，留到后续评估。
